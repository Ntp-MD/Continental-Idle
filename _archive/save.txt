Adversarial review — Continental-Idle
1. Executive summary
The project is in better shape than most codebases its size: ingress normalization is real and layered (normalizeOriginAsset → isSafeSvgMarkup → render-time sanitizeSvgNode), the engine is genuinely framework-free, and the persistence boundary is typed. The dominant risk class is the gap between the invariants the code documents and what it actually enforces:
The advertised “single-writer runExclusive on every CUD” is implemented on ~9 of ~35 commands. The one test that “proves” it only exercises a wrapped command.
The persistence schema enforces hard caps (256 grid rows and columns, 100 floors, 10 000 objects/floor) that no mutation path checks. Because saving is whole-file atomic, crossing any cap makes every future save fail, with a generic error and an in-memory revert.
There is no production persistence path at all — the app boots from an empty seed and depends on a Vite dev middleware.
Security posture is acceptable for a loopback dev tool; I found no working injection bypass. The weakest link is trust-by-static-header plus isTrustedDevOrigin(undefined) === true, which is only defensible because it is loopback by default.
2. Confirmed bugs
[HIGH] Mutation paths don’t enforce the persistence caps; one over-cap entity bricks all saving
Location: src/blueprint-editor/assets/assetUtils.ts:142 (buildWalkableGrid), src/blueprint-editor/domain/types.ts:400-435 (normalizeWalkableGrid/normalizeTileStates, 256 cap), :1599 (MAX_FLOORS), :1068/1609 (MAX_OBJECTS_PER_FLOOR), store/assets.ts:67 (addSvgAsset allows w/h ≤ 10 000), store/mode.ts:23-42 (resizeCanvas), store/floors.ts:10 (addFloor), store/objects.ts:75 (addObject), store/metadata.ts:44 (pasteObjects).
Problem: In-memory construction has no cap; the schema normalizer does. Saving is whole-file atomic, so a single illegal entity makes every save fail.
Failure scenario (concrete): Paste an SVG whose viewBox is 0 0 5000 5000 with the default tileSize 15 → ImportSvgModal.vue:30 sets svgW = 333. addSvgAsset accepts it (≤ 10 000); initAssetFields → buildWalkableGrid(333, 333) creates a 333-row grid. normalizeWalkableGrid rejects anything > 256 → POST /__blueprint-data 400 → the HTTP port retries 3× (≈5 s of backoff) then throws → restoreSnapshot rolls the import back and the user sees only “Failed to save blueprint data”. Same class: resizeCanvas(4000 …) (SettingsModal has min=100 and no max, SettingsModal.vue:340), 101 floors, 10 001 objects (or duplicateFloor of a 10 000-object floor).
Evidence: normalizeWalkableGrid caps rows and columns at MAX_GRID_ROWS = 256 (types.ts:191,401,405); buildWalkableGrid loops row < rows, col < cols from asset.w/h with no bound (assetUtils.ts:148-166); no cap appears in any command (grep for 256/MAX_FLOORS/MAX_OBJECTS_PER_FLOOR under store/ = 0 hits). For w=h=10 000 the same loop allocates 10⁸ cells → tab freeze/OOM (deterministic allocation; OOM itself is Likely, not Confirmed).
Impact: Asset import / canvas resize / heavy authoring can permanently block persistence for the session; at extreme dimensions, a browser lock-up.
Confidence: Confirmed (cap mismatch + failure path); OOM element Likely.
Suggested direction: enforce the same caps in the construction helpers (buildWalkableGrid returns undefined past 256; command-level guards mirroring the normalizer), and surface the specific validation error instead of a generic save failure.
[HIGH] The documented single-writer invariant is not implemented
Location: store/createStore.ts:97-103 (runExclusive), used only in store/assets.ts:64,100,172,190, store/objects.ts:50,76,114,277, store/flatten.ts:32. Not used by store/objects.ts:239 (commitMove), :321 (linkObjects), :352 (unlinkObject), :370 (toggleObjectLock), store/floors.ts (all), store/metadata.ts:44 (pasteObjects), store/tags.ts:14,21, store/mode.ts (all setters), store/npcDefault.ts:43 (updateNpcConfig).
Problem: Read-modify-write commands and save() are not mutually excluded, so the save-point snapshot can be captured after a different command’s mutation.
Failure scenario: command A mutates and calls save(); command B mutates in the same tick and queues its save. Run A builds its body from the already-B-mutated state; A’s HTTP save fails (e.g. 413/500); restoreSnapshot(lastSaved) rolls memory back to before A, silently discarding B; run B then persists the rolled-back state and returns true. B’s caller believes it saved; B’s change is gone from both memory and disk.
Evidence: save() captures lastSaved = captureSnapshot() after the await resolves, reading whatever state currently is (createStore.ts:84); restoreSnapshot installs the snapshot wholesale (:63-72). Only wrapped commands guarantee no interleaving mutation between the mutate and the snapshot. docs/crud-reference.md:7 and AGENTS.md claim every CUD is inside runExclusive.
Impact: On any save failure during overlapping edits, a successfully-reported command is silently lost; the “revert to last saved snapshot” guarantee is violated.
Confidence: Confirmed as an invariant violation; the concrete loss requires a save failure (Likely).
Suggested direction: wrap every mutating command (or move the snapshot capture to the instant the command is enqueued, keyed to the command).
[MEDIUM] Object labels are double-escaped on the canvas
Location: EditorCanvas.vue:752-757 and :1318.
Problem: assetLabel() runs escapeSvgText() (converts &→&amp;, <→&lt;), but the result is emitted through a Vue {{ }} interpolation, which escapes again.
Failure scenario: An asset named Bed & Bath renders on canvas as Bed &amp; Bath; A<B renders as A&lt;B.
Evidence: escapeSvgText is only ever used by assetLabel (grep assetLabel|escapeSvgText → single consumer), and that consumer is a text interpolation, not v-html.
Impact: Cosmetic only (no XSS — Vue escapes). Confirmed.
Suggested direction: return the raw label and let Vue escape.
3. High-risk design problems
[HIGH] No production persistence — the editor only works under Vite dev
Location: src/App.vue:15 (emptySeed()), vite.config.ts:177 (configureServer mounts /__blueprint-data), editorConfig.ts:5.
Problem: The only persistence endpoint exists in the dev server. A production vite build has no backend: boot yields an empty editor and every save fails. BlueprintEditor.vue:59 shows “Failed to load editor” only if reloadEditorData throws; a null load returns silently and renders an empty workspace.
Confidence: Confirmed. Direction: either declare the tool dev-only at build time (fail fast with a clear message) or provide a real endpoint.
[MEDIUM] Two sources of truth for the seed, and a script that silently destroys live data
Location: src/blueprint-editor/data/blueprint-data.json vs the four *.data.ts; scripts/seed-blueprint-data.ts.
Problem: The seed modules and the JSON store are separate data sets that already diverge (the JSON floor has placed objects the seed does not). npm run seed:blueprint-data overwrites the canonical store from the seed, deleting current editor state. The docs say “one-time input” and forbid git checkout restore, but nothing prevents running the script.
Confidence: Confirmed. Direction: guard the script (refuse unless the store is empty or an explicit flag) or generate the seed from the JSON.
[MEDIUM] Portal routing is index-based across different objects with no parity validation
Location: engine/npc/layoutBuild.ts:324-352 (destination key reuses the source spot index), npcEngine.ts:1058-1066 (portalEndpointsByKey.get → missing ⇒ repath-failed), assets/validation.ts:276-316 (no spot-count check).
Problem: A transition target’s destinationPortalKey is built from the source spot index against the destination portal object. If the two portal assets have different interactSpots counts, the destination key does not exist and cross-floor travel silently fails one-way.
Confidence: Likely. Direction: validate matching spot counts for paired portals, or map by post/anchor instead of raw index.
[MEDIUM] Collision is disabled for 19/21 assets
Location: domain/collision.ts:31,54,59.
Problem: objectOverlapsAny returns false for any asset.svg, so SVG objects can be stacked freely; collapsed is dead for them. Placement warnings (“overlaps existing object”) therefore never fire for real assets, and the asymmetry will break any future collision work.
Confidence: Confirmed behavior; whether it is intentional is undocumented.
Direction: decide explicitly (overlap policy per origin/category) and encode it in one place.
[LOW/MEDIUM] Flatten turns decorative art into blocked terrain
Location: store/flatten.ts:139-142 (walkable:false, all-blocked grid) combined with engine/npc/layoutBuild.ts:119 (definition.walkable === false ⇒ blocked unless state walkable).
Problem: Merging decorative SVG furniture yields a solid obstacle NPCs cannot cross (can trap agents or invalidate paths), while overlap is still unchecked (flatten.ts:167).
Confidence: Likely. Direction: default the merged grid to walkable, or make it configurable.
[LOW] Undocumented assumptions
policy.ts:49-53: an unknown agent.roleId silently resolves to defaultRoleId/first role — misconfig is simulated as a different role with no diagnostic.
EditorCanvas.vue:672-688: each arrow-key press calls moveSelectedTo + commitMove → one full HTTP save per keypress, while NPC config edits are debounced; inconsistent flush policy.
4. Security issues
No injection bypass found. Findings are trust-boundary notes, not exploits.
[LOW] Dev persistence endpoint trusts a non-secret header and treats a missing Origin as trusted
Location: vite.config.ts:32-42 (isTrustedDevOrigin returns true when the value is undefined), :77-90 (header gate), store/httpPorts.ts:15.
Problem: The gate is X-Blueprint-Client: 1 + trusted origin + sec-fetch-site. The header value ships inside the client bundle, so it is not a secret. Any local process can read/overwrite the store; with MOD_CLI_ALLOW_LAN=1 any LAN host can too. Cross-site/DNS-rebinding attempts are blocked (Origin/sec-fetch-site checks), and the endpoint is loopback by default.
Confidence: Confirmed. Severity low (dev tool, opt-in LAN).
Direction: acceptable as-is if documented; otherwise bind strictly to loopback and require an operator token for LAN.
[INFO] Render-time sanitizer relies on CSP for url(...)
sanitizeSvgNode (assets/svgSanitizer.ts) strips on*, dangerous style/href schemes, and non-whitelisted tags, but not arbitrary url(...) inside style. Compensating control is the index.html CSP (default-src 'self'). Worth keeping in mind that the sanitizer alone is not sufficient if the CSP is ever relaxed.
5. Test blind spots
The 14 tsx suites + 3 vitest files are real, but the guard on the two riskiest invariants is absent:
The single “concurrency” test only exercises addObject (a wrapped command) — tests/test-store-crud.ts:313. It passes even though commitMove/paintFloorTiles/floor CRUD bypass the queue. runExclusive appears in 0 test lines.
0 tests for resizeCanvas, addSvgAsset, flattenToSvgAsset, commitMove, updateNpcConfig, MAX_GRID_ROWS/256, setAgentFloor.
A broken implementation that skips the 256-cap check at construction, or that omits runExclusive from paintFloorTiles, passes the entire suite.
vitest.config.ts:19 excludes src/engine/** from coverage, so engine coverage is unmeasured (the legacy suites exercise it, but no coverage signal exists).
Failure-recovery paths (save failure + concurrent command) have no test; only test-persistence.ts covers single-command revert.
6. Scalability / reliability risks
Whole-file atomic saves. The store is one 370 KB JSON rewritten on every commit; a 100× project (100 floors × 10 000 objects, ~1 000 assets) means every keystroke-adjacent action rewrites and re-validates the entire file on the single-threaded dev server (vite.config.ts:140-173). The 5 MB MAX_REQUEST_BYTES/MAX_DATA_MODULE_BYTES caps become the hard wall, and half the normalizer caps are hit far earlier.
buildWalkableGrid is O(w·h) unbounded and runs synchronously on asset registration — the one place where a 100× input is a genuine UI hang.
Engine rebuild cost. buildNpcEngineLayout derives rooms per floor and all interaction/queues on start; deriveFloorRooms is O(cells) per floor. Fine today (1 floor, 2 objects); with 100 floors × 10 000 cells it is a multi-second synchronous block on mode switch.
floorPlan.data.ts (305 KB) still ships in the seed path used by tests; the runtime no longer bundles it (verified earlier), so this is a test/boot-fallback cost only.
7. Findings rejected during self-review
namespaceSvgIds misses single-quoted ids (flatten) — rejected: SAFE_SVG_TAGS excludes defs/linearGradient/clipPath/mask/use, so no internal url(#…) references can exist in any stored asset.
reorderFloors off-by-one — rejected: the drop semantics are ambiguous in the UI, and floor array order has no data effect (assignSyncKeys orders by id/label).
sanitizeString is too weak — rejected: it is used on display names only, and all outputs are Vue-escaped; not an HTML sink.
updateNpcConfig stores raw config when normalize fails — downgraded/omitted: the server rejects it and the caller immediately re-saves/reverts.
cloneDeepRaw destroys Map/Set — rejected: no Map/Set is ever stored in reactive state.
A iteration cap (count*2) can miss valid paths* — rejected: the octile heuristic is consistent, so each node is expanded once.
8. Recommended fix order
Enforce persistence caps at construction (#2.1) — cheapest, stops a whole class of bricking; add caps to buildWalkableGrid + a shared assertWithinCaps used by addSvgAsset/resizeCanvas/addFloor/addObject/pasteObjects.
Decide and enforce the single-writer contract (#2.2) — wrap all mutating commands (or move snapshot capture into the enqueue path), then add a test that fails today (e.g. commitMove + paintFloorTiles overlap with a rejecting port) and a test asserting every exported CUD is queued.
Resolve the production-persistence question (#3.1) — either fail fast or add an endpoint; today a production build is silently a dead editor.
Add the missing caps/limits to the UI (SettingsModal max, import w/h feedback) so failures are field-level, not “Failed to save”.
Fix the double-escaped label (#2.3) — one-line, user-visible.
Portal spot-count validation (#3.3) and flatten walkable default (#3.5) — correctness of engine-visible behavior.
Guard seed:blueprint-data (#3.2).
Security hardening (#4.1) only if LAN mode is meant to be supported.
No files were modified. I have not started any fix.
